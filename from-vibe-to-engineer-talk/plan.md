# План доповіді «Від вайбкодінгу до AI-інженерії»

Аудиторія: розробники команди. Формат: ~35–40 хв, практичне першочергово.
Базується на рісьорчі з vault (головна нота: `Inbox/Доповідь — Від вайбкодінгу до AI-інженерії.md`).

## Центральна теза

**AI не визначає якість софту. Її визначає процес, у який ти ставиш AI.**

- Вайбкодінг = AI без процесу → наратив «якість падає» тут правдивий.
- AI-інженерія = AI у процесі → якість росте, бо людський час перетікає на архітектуру, дизайн, планування, рев'ю.
- Вайбкодінг і AI-інженерія — різні інструменти для різних задач, не сходинки якості.
- Harness — командна інвестиція, не індивідуальний хак.

## Структура по пунктах

### 1. Hook — інтернатура (3')
Історія: лід групи інтернів, сам код не писав — збирав систему з блоків, рев'ю було критичним. «Те саме відчуття я отримав місяць тому. Тільки не з людьми — з AI-агентом.»
- Підкріплення: Karpathy описує агента так само — «надзвичайно здібний стажер»; головним завданням людини стає смак, архітектурне бачення, специфікації, нагляд.
- Джерела: `Resources/Andrej Karpathy From Vibe Coding to Agentic Engineering.md`

### 2. Акт 1 — що таке вайбкодінг і чому це прекрасно (3–4')
- Визначення: створення софту без занурення в технічні деталі, людською мовою (`Resources/Vibe coding.md`).
- Бар'єр входу впав: сайт/апка за один промпт. Ідеально для: прототип, лендінг, особисті тулзи.
- Чому це **не про нас**: одноразовість + «не занурюватись» = борг у shared codebase.

### 3. Поворот + quality-pivot (4')
- Наратив «AI знижує якість» — правдивий лише для вайбкодінгу.
- Перевертаємо: *«Bad code is the most expensive it has ever been. If your codebase is a mess, AI cannot help you»* (Matt Pocock, з атрибуцією).
- AI не деградує якість — він робить поганий код дорожчим → fundamentals критичніші, ніж будь-коли.
- Звільнений час → архітектура, дизайн, TDD. (Karpathy: потреба в TDD з agentic engineering стала критичною.)

### 4. Role shift — еволюція ролі інженера (4–5')
- Розкрутка інтерн-аналогії: ти збираєш систему, агент реалізує. Рев'ю — несуча навичка.
- Щоб рев'ювити — треба самому бути сильним (вбиває міф «джуни = сеньйори»). Планка експертизи **росте**.
- Pocock: *«AI is a brilliant tactical programmer — a sergeant. A sergeant needs a strategist, and that strategist is you.»*
- Karpathy: «Можете передати на аутсорс своє мислення, але не можете передати розуміння».
- Приклад-якір: «я знаю, який рядок змінити — міг би за хвилину. Але прошу агента: він напише тест, додасть доки, знайде кейси, які я не побачив. Це не магія — це процес, який цього вимагає.»
- Приклад масштабу: Codex harness engineering — «0 рядків коду людьми», «люди керують — агенти виконують» (`Resources/Harness engineering codex.md`).
- ⚠️ Не фреймити як «AI = дешева робоча сила джунів» — акцент на трансформації *моєї* ролі.

### 5. Планування — чому без нього ніяк (8')
*Це не «корисна звичка», а несучий механізм AI-інженерії. Два акценти:*

**5a. Узгодження розуміння — спершу з собою, потім з агентом**
- Pocock про BDD: «ніхто не знає точно, чого хоче» — проблема не нова, AI її лише загострив.
- Подвійний ефект планування: **по-перше, ти формалізуєш для себе**, що насправді хочеш зробити (часто саме тут з'ясовується, що не розумів); **по-друге, пояснюєш моделі** — узгоджуєш спільне розуміння до того, як написано перший рядок коду.
- Раніше пояснював задачу гумовій качечці; тепер качечка **відповідає**. `grill me` prompt: попроси агента допитати тебе — допит витягує дірки в розумінні.
- Прояснення стало durable-артефактом, а не випадковим інсайтом. Це точка, де людина *керує*.

**5b. Приклад: SDD / OpenSpec — процес, поставлений по фазах**
- Як виглядає планування, доведене до дисципліни: **Specify** (що, навіщо) → **Plan** (як саме) → **Tasks** (декомпозиція) → **Виконання** (`Resources/SDD.md`).
- Spec ≠ Plan: spec — what/why (вимоги, acceptance-критерії без технології), plan — технічне рішення. Розділення змушує не перестрибувати з «хочу фічу» одразу в код.
- Кожна фаза дає агенту релевантний контекст саме для цього кроку — замість one-shot prompt з усім одразу (рішення проблеми context bloating, `Notes/We should learn how to SDD.md`).
- OpenSpec як lightweight-приклад: `propose → apply → archive`. Особистий досвід: прокатано на двох реальних проєктах (Moby Dick bot, neuro-vault MCP) — показати 2–3 живих кадри (скріншоти propose → apply). Після відмови від демо саме цей блок несе вимогу «приклади з реальних задач».
- ⚠️ Показуємо фази як приклад дисципліни процесу, не розкладаємо на «дві осі» і lifecycle — це окрема SDD-доповідь.

### 6. Практики, інструменти, правила: skills / rules / ADR (7')
*(блок під вимогу таски — що команда може взяти собі)*
- **Rules / контекстні файли (AGENTS.md / CLAUDE.md):** писати руками, не генерувати — згенеровані знижують успішність задач на ~3% і здорожчують роботу агента на 20%+ (`Resources/AGENTS md checklist.md`, Evaluating AGENTS.md paper). Короткий чекліст «як правильно».
- **Skills:** пакування експертизи в перевикористовувані навички. Приклади: improve-codebase-architecture (Pocock синтезував «A Philosophy of Software Design» у skill), teach skill (onboarding у проект). Skills бувають stateful/stateless.
- **ADR:** код показує *що*, але не *чому*. ADR = інституційна пам'ять про рішення, append-only, лежить поряд з кодом — і людина, і агент читають «чому саме так» (`Resources/ADR.md`).
- **Context engineering** (одним слайдом): write / select / compress / isolate — те, що об'єднує всі три практики (`Resources/Context Engineering.md`).

### 7. Висновки + Call to action (4')
- Harness — командна інвестиція: в інтернів вкладаєшся ти, в агента — обв'язка репо.
- Аналогія з CI/CD: колись примха ентузіаста, тепер норма. Процес став дешевим впроваджувати.
- Рекомендації «що почати завтра»: завести/перевірити AGENTS.md по чекліст, перший ADR, перший shared skill, домовитись про рев'ю-практику для AI-коду.

### 8. Land (2')
- Відкрите питання залу (фінальне формулювання — TBD).
- Тизер: «як саме будувати spec-частину — окрема розмова, скоро» (SDD-доповідь).

**Разом: ~36–38 хв.** Живе демо прибрали свідомо — його 10' розподілені: планування виросло до 8' (5b зі скріншотами реальних флоу), практики до 7'. Якщо час тисне — скорочувати 5b до одного слайда з фазами, але акцент 5a «формалізуєш для себе → пояснюєш моделі» не чіпати.

## Чого свідомо не робимо
- ❌ «Вайбкодінг = зло» — він прекрасний, просто для іншого.
- ❌ AI-first overview без практики — інженери цей шум знають.
- ❌ Глибоко в SDD / дві осі / lifecycle OpenSpec — це окрема доповідь (`Inbox/Доповідь — Дві осі SDD.md`).
- ❌ Інтерн-аналогія як «AI = дешеві джуни».
- ❌ Живе демо — прибрали свідомо; реальні флоу показуємо статичними кадрами в 5b.
