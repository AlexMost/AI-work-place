OpenSpec internals · Урок 1

Prompt compiler: як CLI склеює промпт

Після цього уроку ти зможеш пояснити кожен рядок виводу openspec instructions — тобто відтворити і захистити тезу демо №1 своєї доповіді.

Зв'язок з місією

Це механіка під демо №1 («CLI під капотом»). Усі цитати — з сирців Fission-AI/OpenSpec v1.5.0 (твої демо перевірені на 1.3.1, bridge-baseline — 1.4.1: механіка та сама, номери рядків можуть трохи плисти).

3. Звідки береться схема: триступеневий fallback

# resolveSchema() / getSchemaDir() — artifact-graph/resolver.ts:63-153
1. <repo>/openspec/schemas/<name>/schema.yaml   ← project (так «встановлено» bridge)
2. $XDG_DATA_HOME/openspec/schemas/<name>/     ← user override
3. <npm-пакет>/schemas/<name>/                 ← built-in (spec-driven)

Перший збіг перемагає. Саме тому інсталяція superpowers-bridge — це буквально cp -r у openspec/schemas/, без жодної реєстрації. Перевірити, звідки резолвиться схема (і чи не «затінює» вона built-in): openspec schema which <name>; шляхи темплейтів — openspec templates.

5. Анатомія промпта: кожна секція має рівно одне джерело

Порядок emission — дослівно з printInstructionsText (instructions.ts:172-289). Це і є «prompt compiler»: жодної генерації, лише детермінована склейка.

Retrieval: закрий таблицю і назви по пам'яті — які дві секції приходять з config.yaml, які три зі schema.yaml?

З config.yaml: <project_context> (глобальний context) і <rules> (rules[artifactId]). Зі schema.yaml: <task> (description), <instruction> (instruction) і <template> (файл templates/). Решта — граф і файлова система.

6. Стан = файлова система, і крапка

«CLI тримає стан» означає буквально: завершеність артефакту = існування його файлів. detectCompleted (state.ts:14-29) проганяє artifactOutputExists (outputs.ts:40), який резолвить generates-патерн через fast-glob. «Blocked» = хтось із requires не в множині завершених. Ні бази, ні прихованого стейту — видалиш design.md, і DAG чесно відкотиться.

Прогрес apply-фази парситься regex-ом (instructions.ts:305):

/^[-*]\s*\[([ xX])\]\s*(.+)\s*$/

Саме тому bridge-схема так наполягає: «Tasks not using - [ ] won't be tracked» — це не побажання, це межа можливостей парсера.

Тизер уроку 2: а куди вставляти TDD?

apply — не артефакт і не CLI-команда, а окремий блок схеми (apply: {requires, tracks, instruction}). generateApplyInstructions (instructions.ts:331-433) читає лише schema.apply — і жодного разу не викликає readProjectConfig(): context: і rules: з config.yaml в apply-промпт не потрапляють взагалі. Єдиний прямий вхід у apply — apply.instruction у schema.yaml. Тому superpowers-bridge — це саме схема, і тому TDD туди заходить через неї. Розберемо в уроці 2.

7. Перевір себе

1. Звідки openspec instructions дізнається, яку схему використовувати для вже існуючої зміни?

2. Що з config.yaml потрапить у промпт артефакту design?

3. Як CLI визначає, що артефакт proposal завершений?

4. Ти додав rules: { apply: [«пиши тест перед кодом»] } у config.yaml. Що станеться?

8. Практика в реальному терміналі (5 хв)

Feedback loop — твій власний проєкт. Якщо локальна версія openspec старша за 1.4, запускай через npx @fission-ai/openspec@latest.

# 1. Звідки резолвиться схема? Очікуй: project (openspec/schemas/…)
cd ~/git/svadlenka-crm && npx @fission-ai/openspec@latest schema which superpowers-bridge

# 2. Звідки беруться темплейти? Очікуй: шляхи всередині openspec/schemas/superpowers-bridge/templates/
npx @fission-ai/openspec@latest templates

# 3. Скомпілюй промпт для будь-якої активної зміни і ЗНАЙДИ в ньому:
#    - свій context з config.yaml (секція <project_context>)
#    - своє ADR-правило з rules.design (секція <rules>)
#    - «Use the Skill tool…» з schema.yaml (секція <instruction>)
ls openspec/changes
npx @fission-ai/openspec@latest instructions design --change <назва>

Якщо всі три знахідки зійшлися з таблицею з §5 — урок засвоєно: ти щойно верифікував prompt compiler на власному проді.
