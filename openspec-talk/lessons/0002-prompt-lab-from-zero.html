OpenSpec internals · Урок 2 · Лабораторія

Що впливає на промпт: сетап з нуля

Голий OpenSpec, без bridge. Чиста тека, 6 експериментів, і в кожному ти спочатку прогнозуєш, потім запускаєш, потім звіряєш. Всі «очікувані виводи» перевірені на живому CLI (v1.5.0) сьогодні.

Формат лабораторії

У кожному експерименті: 🔮 Прогноз (сформулюй відповідь уголос, потім розгорни підказку) → ⌨️ Команди → ✅ Перевірка. Прогноз перед дією — це retrieval practice: саме він, а не читання, будує довгу пам'ять.

Експеримент 0 — Сетап: що насправді створює init?

🔮 Прогноз: скільки файлів і яких створить openspec init у порожньому репо?

Рівно 9: вісім слеш-команд у .claude/commands/opsx/ і один openspec/config.yaml. Ні схем, ні шаблонів — вони живуть у npm-пакеті.

alias ops="npx -y @fission-ai/openspec@latest"   # щоб не тягати повне ім'я пакета
mkdir opsx-lab && cd opsx-lab && git init
ops init --tools claude .
find . -type f -not -path "./.git/*" | sort

✅ Побачиш 8 команд (apply, archive, explore, ff, new, propose, sync, verify) + openspec/config.yaml. Відкрий конфіг: він уже містить закоментовані приклади context: і rules: — розробники підказують два головні важелі впливу на промпт.

Експеримент 1 — Зміна: де вона тримає свою схему?

ops new change try-prompt
find openspec/changes -type f
cat openspec/changes/try-prompt/.openspec.yaml

✅ У теці зміни рівно один файл, і в ньому два рядки:

schema: spec-driven
created: 2026-07-01

Це пін схеми per-change (урок 1, §2): зміна назавжди знає свою схему сама, а schema: у config.yaml — лише default для нових змін.

Експеримент 2 — Базовий промпт: скільки секцій без жодного конфігу?

🔮 Прогноз: які секції будуть у промпті proposal, поки config.yaml порожній, а залежностей немає?

Шість: <artifact>-обгортка, <task>, <output>, <instruction>, <template>, <success_criteria>, <unlocks>. Без <project_context>, <rules>, <dependencies> (у proposal requires: []).

ops instructions proposal --change try-prompt > baseline.txt
grep -nE "^</?[a-z_]+|^<artifact" baseline.txt    # трюк: показати лише скелет секцій

✅ ~68 рядків, секції: artifact → task → output → instruction → template → success_criteria → unlocks. Запам'ятай цей скелет — далі дивимось, що і куди «вклинюється».

Експеримент 3 — config.yaml: хірургічна інжекція

🔮 Прогноз: додаємо context + rules.proposal + свідомо битий ключ rules.bogus-artifact. Скільки нових секцій, де саме, і що станеться з битим ключем?

Дві нові секції — <project_context> і <rules> — рівно між <task> і <output>. Битий ключ не ламає нічого: warning у stderr з переліком валідних ID (resilient-парсинг конфігу, урок 1 §2).

Заміни openspec/config.yaml на:

schema: spec-driven

context: |
  Tech stack: TypeScript + Fastify + SQLite.
  Money is stored as integer cents, never floats.

rules:
  proposal:
    - Keep the proposal under 300 words
    - Always include a "Non-goals" section
  bogus-artifact:
    - This key does not exist in the schema
ops instructions proposal --change try-prompt > enriched.txt
diff baseline.txt enriched.txt

✅ Перевір три речі:

  • diff показує +12 рядків одним блоком після <task> — обидві секції з коментарем «Do NOT include this in your output»;
  • у stderr: Unknown artifact ID in rules: "bogus-artifact". Valid IDs for schema "spec-driven": design, proposal, specs, tasks;
  • решта промпта — байт-у-байт та сама. Інжекція хірургічна, не «переписування».

Експеримент 4 — Заблокований артефакт: warning, а не заборона

ops instructions tasks --change try-prompt

✅ tasks вимагає specs і design, яких нема, — але CLI все одно компілює промпт, лише додає зверху:

<warning>
This artifact has unmet dependencies. Complete them first or proceed with caution.
Missing: specs, design
</warning>
…
<dependency id="specs" status="missing">
  <path>…/openspec/changes/try-prompt/specs/**/*.md</path>

І зверни увагу: <project_context> з конфігу з'явився і тут — context глобальний, він іде в промпт кожного артефакта. DAG у OpenSpec — порадник, а не поліцейський: рішення завжди лишається за агентом/людиною.

Експеримент 5 — Форк схеми: переписуємо instruction і перепинаємо зміну

ops schema fork spec-driven lab-schema
find openspec/schemas -type f
ops schema which lab-schema      # Source: project
ops schema which spec-driven     # Source: package (шлях у npm-кеш)

Тепер відкрий openspec/schemas/lab-schema/schema.yaml і додай перший рядок у instruction: артефакта proposal — маркер, який неможливо не помітити:

  - id: proposal
    ...
    instruction: >
      >>> LAB MARKER: this line comes from the FORKED schema <<<
Пастка block scalars (перевірено на собі)

В артефактах spec-driven інструкції — folded scalar (instruction: >), а в apply: — literal (instruction: |). Перший непорожній рядок блоку фіксує базовий відступ: вставиш рядок із 6 пробілами там, де контент має 4 — отримаєш All mapping items must start at the same column. Після будь-якої правки схеми одразу: ops schema validate lab-schema.

Зміна try-prompt досі запінена на spec-driven. Перемкни її, відредагувавши метадату зміни (не config!):

sed -i '' 's/^schema: spec-driven/schema: lab-schema/' openspec/changes/try-prompt/.openspec.yaml
ops instructions proposal --change try-prompt | head -1
ops instructions proposal --change try-prompt | grep "LAB MARKER"

✅ Перший рядок: <artifact id="proposal" change="try-prompt" schema="lab-schema">, і твій маркер сидить усередині <instruction>. Ти щойно зробив те саме, що робить superpowers-bridge — підмінив схему, не чіпаючи ні CLI, ні слеш-команди.

Експеримент 6 — Apply: інший світ

🔮 Прогноз: у apply-промпті буде твій context («Money is stored as integer cents…») і rules?

Ні. generateApplyInstructions читає лише schema.apply і взагалі не викликає readProjectConfig() — жодна секція з config.yaml в apply не потрапляє (instructions.ts:331-433, урок 1 §6).

ops instructions apply --change try-prompt     # поки tasks.md нема

✅ ### ⚠️ Blocked — Missing artifacts: tasks (в apply.requires spec-driven стоїть лише tasks). Створи трекінг-файл руками і повтори:

cat > openspec/changes/try-prompt/tasks.md <<'EOF'
## 1. Setup

- [ ] 1.1 Create fastify server
- [x] 1.2 Init sqlite schema
EOF
ops instructions apply --change try-prompt

✅ Звір із цим (реальний вивід):

## Apply: try-prompt
Schema: lab-schema

### Context Files
- tasks: …/openspec/changes/try-prompt/tasks.md

### Progress
1/2 complete

### Tasks
- [ ] 1.1 Create fastify server
- [x] 1.2 Init sqlite schema

### Instruction
Read context files, work through pending tasks, mark complete as you go.
Pause if you hit blockers or need clarification.

Три спостереження:

  • Формат інший: markdown-заголовки, а не XML-теги — apply збирає окремий принтер, не printInstructionsText;
  • Progress: 1/2 — це regex /^[-*]\s*\[([ xX])\]/ по tasks.md, більше нічого;
  • твого context/rules тут немає. Хочеш вплинути на apply — редагуй apply.instruction у своїй схемі (спробуй: додай туди маркер і повтори команду) або клади знання в самі артефакти (tasks.md, design.md), які apply перелічує як Context Files.

Синтез: повна карта впливу на промпт

ДжерелоПромпт артефактаПромпт apply
config.yaml → context✅ <project_context>, у всіх артефактах❌
config.yaml → rules.<id>✅ <rules>, лише в артефакті <id>❌
schema.yaml → description / instruction / generates✅ <task> / <instruction> / <output>❌
schema templates/*.md✅ <template>❌
schema.yaml → apply.instruction❌✅ ### Instruction
граф + файли на диску✅ <warning>/<dependencies>/<unlocks>✅ Blocked / Context Files / Progress
.openspec.yaml змінивибирає, яка схема взагалі використовується (пін per-change)

Перевір себе

1. Треба перемкнути вже існуючу зміну на іншу схему. Що редагуєш?

2. Звідки береться рядок «Progress: 1/2 complete» в apply-промпті?

3. Додаєш у config.yaml rules: { specs: [«кожна вимога — testable»] }. Де це правило з'явиться?

Первинне джерело

Після лабораторії прочитай сам built-in schemas/spec-driven/schema.yaml (≈250 рядків, 5 хвилин): тепер ти знаєш, куди «їде» кожне його поле. Він у тебе вже і локально — openspec/schemas/lab-schema/schema.yaml — це його копія.
