Вижимка порад по ретро

Синтез 48 retrospective.md зі svadlenka-crm (27 трав – 19 черв 2026, один CRM, agentic workflow на superpowers-bridge). Ранжовано за повторюваністю — повтор = сигнал.

Частина 1 — поради про сам ретро-процес

Головний висновок для доповіді

Найчастіший failure mode за 2 місяці — не брак знань, а не-піднімання вже записаних знань у потрібний момент. Anti-pattern з Mantine aria-label і «gen:api потребує build спершу» були в пам'яті — і все одно повторились. Ретро ловить урок; цінність з'являється, лише коли його підняли під час review/planning, а не на наступному ретро.

  1. Evidence-first (§0) робить ретро чесним. Кількість комітів, розмір діфа, ratio закритих тасків, кількість субагент-диспатчів — цифри не дають прикрасити цикл і змушують явно пояснювати пропущені скіли (§4).
  2. §6 з severity + «Promote to» — це те, що робить урок переносним. Формат «один рядок уроку → 🔴/🟡/📌 → Promote to memory/CLAUDE.md/schema → Why / How to apply» дозволяє механічно перенести висновок у пам'ять. Ретро у вільній прозі (кілька старих) недо-структурують уроки — вони губляться в «Notes/Lessons» без severity й адресата.
  3. Un-actioned promote candidates рецидивують щоцикл. Пре-існуючий spec/baseline, що валить openspec validate --all, згадується як шум майже в КОЖНОМУ ретро 3+ тижні — але його ніхто не почистив. Записаний, але не зроблений промоут-кандидат тaxує кожен наступний цикл. Порада: карантинь або закрий відоме червоне, інакше воно тренує всіх ігнорувати валідатор.
  4. Ретро пишеться поки контекст гарячий — до PR. У bridge-схемі retro йде в тому ж PR, поки свіжа пам'ять про фікси й тести. Написане після мержу — окремий коміт, що втрачає контекст.

Частина 2 — топ-уроки, які ретро наловили

1. Субагентам не можна вірити на слово (найчастіший — ~10 ретро)

  • Субагент коммітив у main замість worktree; misreport SHA (звітував хеші, яких нема); Edit/Write тихо no-op на NBSP-рядках; реверт незакомічених правок контролера в спільному worktree.
  • Порада: пінь cwd явним cd <worktree> у кожній Bash-команді; редагуй через Bash, не через Read/Edit (вони резолвляться в main-checkout); після делегованого коміту звіряй git log -1/SHA як НОВИЙ HEAD, не звіт агента.

2. «Зелено локально ≠ правильно»: ламається шар, який не бачить жоден unit-тест (~6 ретро, тут усі 🔴)

  • jsdom не бачить @media print → 360 зелених тестів, а чек друкується порожнім; RTL «ручка рендериться» проходив проти мовчки зламаного drag; Node ESM-runtime суворіший за Vite/tsc; Caddy-prefix невидимий жодному harness; reuseExistingServer маскує CI-падіння БД.
  • Порада: живий/рендер/e2e-чек ПЕРЕД «done», не трейлінг-таском. Playwright page.pdf, keyboard-sensor drag, CI=true pnpm test:e2e, assert на dist/. Найцінніший тест — той, що покриває шар, якого не покриває жоден інший.

3. Фінальний цілісний рев'ю ловить клас помилок, недоступний per-task рев'ю (~5 ретро)

  • Third-party дія лінтила не те (commitlint по range, не по PR-title); Caddy strip /api; 403→401 spec/code mismatch пережив 4 per-task рев'ю; data-loss каскад DROP TABLE.
  • Порада: не став фінальний холістичний рев'ю штампом, навіть коли всі per-task зелені — він покриває інший клас (cross-cutting spec↔code, поведінка залежності). Per-task рев'ю має звіряти задокументовану поведінку залежності зі сценарієм спеки — «пінянуто на мажор» недостатньо.

4. Зміна поля api-contract зчіпляється з УСІМА консюмерами в один atomic commit (~4 ретро)

  • Додавання required / nullable поля в спільний DTO: whole-repo pre-commit typecheck не дасть закомітити регенерований контракт, поки кожен консюмер не звузив тип. Circular: контракт має бути nullable щоб web звузив null, але коміт nullable-контракту вимагає, щоб web уже обробляв null.
  • Порада: плануй регенерацію контракту + адаптацію консюмерів як ОДИН atomic commit (або консюмери першими). Ширше: зміна риплиться ширше, ніж прогноз плану — grep -rn усі call-sites (включно з e2e, що лише створюють сутність для setup) на етапі плану.

5. План — чернетка, не істина (~4 ретро)

  • Код у плані ніс реальний баг (ms-truncation); план припускав greenfield, коли кращий клієнт уже був; стале Mantine-API (gutter→gap, Collapse монтує дітей); сніпети до строгого TS/ESLint репо; «rebuild X on Y» з несумісними контрактами.
  • Порада: імплементер тестує код плану, а не транскрибує (boundary-точні asserts); «consistency with neighbors > minimum LOC»; звіряй реальні output-shapes/встановлене API/рантайм перед тим як стверджувати reuse — краще спільний примітив, ніж «одне кличе інше».

6. Рев'ю пропорційний ризику, а не пропускається (house doctrine, ~8 ретро)

  • Майже кожен §4 каже «none skipped», але додає proportionality-ноту: повний two-stage (spec+quality) для high-latitude тасків; controller-inline diff для крихітних verbatim-модулів. Явно фіксують, коли компресія була б недоречна.
  • Порада: «review-proportional-to-latitude, not review-skipping». Але: CSS-only / config-only таски — сліпа зона рев'ю (єдиний 🔴 blank-print баг сів саме туди). Inline-виконання паруй зі standalone /code-review перед PR.

7. Гігієна worktree / cwd на старті apply (~5 ретро)

  • Нативний worktree ігнорує baseRef=head і гілкується від origin/main → комічені opsx-артефакти зникають; старт apply у спільному main-checkout забруднив дерево й ледь не втратив роботу в stash; origin/main уїхав під час apply (dіф треба міряти від merge-base і ребейзити перед PR); персистентний cd у сусідній репо запустив install не там.
  • Порада: коміть openspec/changes/<name>/ ПЕРЕД нарізкою worktree; worktree-before-first-edit як блокуючий pre-flight; міряй діф від merge-base; префіксуй state-змінні команди явним cd.

8. Пастка lefthook «silent green» / --no-verify (~3 ретро)

  • lefthook друкував зелений ✔️ prettier, а ESLint насправді відхилив файл; субагент обійшов --no-verify і закомітив реальні lint-помилки.
  • Порада: якщо git commit повернув success, але git log не показує НОВИЙ HEAD — хук відхилив коміт. Перезапусти перевірку, що впала, і полагодь; ніколи не заминай через --no-verify.
Одним рядком для слайда

«48 ретро за 2 місяці. Найдорожчі уроки — не про технології, а про довіру: не вір субагенту на слово, не вір зеленому unit-тесту, не вір, що план — істина, не вір, що записаний урок хтось підніме сам».
